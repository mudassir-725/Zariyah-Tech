V2 objective
V2 should deliver a tested backend identity platform before we connect or expand the UI:
Authentication
+ User Profiles
+ PostgreSQL
+ OAuth
+ JWT/session handling
+ Profile CRUD
+ API endpoints
+ OpenAPI
+ Postman testing
+ Security hardening
The current V1.37 authentication modal becomes the frontend contract, not the backend implementation.
________________________________________
 Recommended V2 architecture
Frontend UI        Existing V1.37
Backend            NestJS + TypeScript
Architecture       Modular monolith
HTTP adapter:       Express
API                 REST under /api/
Database            PostgreSQL
ORM                 Prisma
Authentication      Passport + OAuth/OIDC
Access token        Short-lived JWT
Refresh session     Rotating random token in secure cookie
Documentation       OpenAPI / Swagger
Testing             Jest + Supertest + Postman CLI
Local environment   Docker Compose

NestJS already provides established patterns for authentication, guards, validation, testing, and generated OpenAPI documentation, making it suitable for a backend-first modular monolith. 
PostgreSQL remains the correct database because users, profiles, identities, sessions, roles, and later organizations and projects are relational. JSONB can still handle genuinely flexible metadata, while Prisma provides CRUD, migrations, and transactions.

 Authentication model
Registration
Validate request
→ Normalize email and username
→ Verify uniqueness
→ Hash password
→ Create user and profile transaction
→ Create verification token
→ Send verification email
Passwords should use Argon2id rather than reversible encryption or enthusiastic improvisation with SHA-256. OWASP currently recommends Argon2id as the preferred password-hashing algorithm. 
Login
Verify credentials
→ Create short-lived access JWT
→ Create rotating refresh session
→ Set secure refresh cookie
→ Return safe user profile
Token strategy
Use:
Access JWT: approximately 15–20 minutes
Refresh session: approximately 7–30 days
The refresh token should be:
•	Random rather than user-readable 
•	Stored as a hash in PostgreSQL 
•	Rotated after every refresh 
•	Revocable per device 
•	Grouped into token families 
•	Checked for token-reuse attacks 
Do not store either token in localStorage.
Secure browser sessions should use HttpOnly, Secure, and appropriate SameSite cookie settings. Refresh rotation and CSRF protection should be part of the design rather than decorative security terminology added after launch. 
OAuth/OIDC
Providers:
Google
Apple
GitHub
Provider identities should be stored separately from the internal user account.
The backend must define rules for:
•	Existing-email collisions 
•	Explicit account linking 
•	Provider account removal 
•	Provider callback validation 
•	OAuth state 
•	OIDC nonce 
•	Issuer and audience validation 
OIDC should be used for authentication identity, while OAuth handles delegated authorization.

V2 definition of done
V2 is complete when:
•	Database migrations work from an empty PostgreSQL database 
•	Registration, login, refresh, logout, and recovery work 
•	Google, Apple, and GitHub sign-in work 
•	Profile CRUD works 
•	Session revocation works 
•	Client and Admin authorization works 
•	Every endpoint is documented in OpenAPI 
•	Postman collections are committed and automated 
•	Tests run in CI 
•	Tokens never enter browser local storage 
•	Passwords and tokens never appear in logs 
•	Staging runs over HTTPS 
•	Health checks, backups, and environment documentation exist 
•	The V1.37 authentication UI can connect without changing the API contract
